# Import episode transcripts

The public `/history` page searches completed transcripts generated by `bbpc-pipeline`. The importer runs from this monorepo. Full pipeline runs invoke `pipeline.mjs` immediately after successful transcription; the commands below remain available for reviewed archive imports and manual retries.

The pipeline adapter reuses these same target checks, passage limits, inspection, and atomic import behavior. It maps the original audio filename by exact recording date, or accepts a verified episode ID. The pipeline's `--only import_transcript --confirm-complete` imports an existing reviewed file; add `--dry-run` for read-only inspection. Both the pipeline checkout and this monorepo checkout (with dependencies installed) are required for automatic imports.

Use Node 22.6.0+ (required for `--experimental-strip-types`) and root pnpm workspaces. Deploy the new backend schema/functions and shared contract before deploying the web change. The normal deployment target/environment checks and separate production approval/runbook still apply. This tool imports data; it never deploys a backend.

## Prepare a mapping

Keep transcript files and the mapping outside the repository. A mapping is a JSON array:

```json
[
  { "file": "20260101.json", "episodeId": "CANONICAL_CONVEX_EPISODE_ID", "complete": true }
]
```

Generate this mapping by matching `YYYYMMDD.json` filenames to exact episode recording dates. Configure the pipeline JWT and expected-target environment variables described below, then run from the repository root:

```sh
pnpm --filter @tonyisup/bbpc-convex-api transcripts:map \
  --source /Users/juicebox/src/bbpc/bbpc-pipeline/transcripts/20260908.json \
  --output /private/tmp/bbpc-transcript-mapping.json \
  --url "$BBPC_EXPECTED_CONVEX_URL"
```

Use the transcripts directory as `--source` to map the archive. The script reads immediate `.json` filenames and calls the existing authenticated `pipeline.content.getEpisodeByDate` query; it does not upload transcripts or change episodes. For example, `20260908.json` resolves recording date `2026-09-08`. Invalid filenames/calendar dates, missing episodes, ambiguous dates, and repeated episode IDs fail the batch before output is written. Existing output files are never overwritten. Keep the output outside the source directory so directory imports do not treat it as a transcript.

Generated entries default to `complete: false`. After verifying all source transcripts finished, either set each verified entry to `complete: true`, or generate a new output with `--confirm-complete`. This is a completion assertion, not automatic detection.

For a manual mapping, replace the placeholder with the episode's actual Convex document ID. Do not use episode numbers or legacy IDs. The importer verifies every mapped ID through `episodes.transcripts.inspect` before making any writes; inspect output includes episode number for review. No fuzzy title/date inference occurs.

`complete: true` is the operator's explicit confirmation that transcription finished. The producer saves partial files when interrupted, so file existence and valid JSON are insufficient. Confirm completion from pipeline logs and source-audio coverage before setting it. A directory import requires a mapping for every `.json` file in that directory, with no repeated episode IDs or filenames.

## Validate offline

```sh
pnpm --filter @tonyisup/bbpc-convex-api transcripts:import \
  --source /absolute/path/to/transcripts \
  --mapping /absolute/path/to/mapping.json
```

`--source` also accepts one JSON transcript file. Offline validation checks format/completion/size and emits a text-free manifest, but cannot verify that episode IDs exist. Malformed files fail before any writes. Whitespace-only segments are skipped; negative/nonfinite/reversed/out-of-order timestamps fail with a segment index. The input limit is 8 MiB per JSON file, with 50,000 source segments and 512 KiB of source text. The resulting search passages also must fit the limits below.

## Inspect the intended backend, then apply

**`BBPC_PIPELINE_ACCESS_TOKEN` requires a short-lived Clerk M2M JWT. Convex deploy keys do not work as pipeline tokens.** A Clerk machine secret must first be exchanged for a JWT; it cannot be supplied directly either. Pass the JWT without a `Bearer` prefix. The service principal needs `pipeline:publish`, and normal application-write/client-version gates apply.

If you already have a valid pipeline JWT in `CONVEX_PIPELINE_TOKEN`, reuse it:

```sh
export BBPC_PIPELINE_ACCESS_TOKEN="$CONVEX_PIPELINE_TOKEN"
```

For this local pipeline checkout, mint a short-lived JWT using its existing Clerk helper and configured machine secret. This captures the JWT in the shell environment without printing it or saving it to a file:

```sh
BBPC_PIPELINE_ACCESS_TOKEN="$(
  /Users/juicebox/src/bbpc/bbpc-pipeline/venv/bin/python - <<'PY'
import sys
from dotenv import dotenv_values
sys.path.insert(0, "/Users/juicebox/src/bbpc/bbpc-pipeline")
from lib.convex_client import ClerkM2MTokenProvider
config = dotenv_values("/Users/juicebox/src/bbpc/bbpc-pipeline/.env")
try:
    token = ClerkM2MTokenProvider(machine_secret_key=config["CLERK_MACHINE_SECRET_KEY"])()
except Exception:
    sys.exit("Could not mint a pipeline JWT; check the pipeline's Clerk machine configuration.")
sys.stdout.write(token)
PY
)" && export BBPC_PIPELINE_ACCESS_TOKEN
```

The configured Clerk machine must be trusted by your intended dev backend's issuer/audience configuration and authorized service principal. Restoring database rows alone does not configure Convex environment variables. This command does not select or change the Convex target; retain the expected dev target settings below. Rerun it when the short-lived JWT expires. Never put tokens in mapping files or pass their values as command-line arguments.

### Troubleshooting authentication after restoring dev

There are two different Clerk machine IDs:

- The **sender** is the pipeline machine whose `CLERK_MACHINE_SECRET_KEY` mints the JWT. Its ID appears in the JWT's `sub` claim and in the dev database's service-principal registration.
- The **receiver** is the Convex machine included in the sender's allowed scopes. Its ID appears in the JWT's `aud` claim and must equal `CLERK_M2M_AUDIENCE` on the Convex deployment and in the pipeline configuration. Do not set this variable to the sender ID.

`NoAuthProvider` lists the providers Convex accepts, not the identity in the submitted token. Compare the fresh JWT's `iss` and `aud` with that list; changing a local audience variable does not change Clerk's minted claims. After changing machine credentials or scopes, mint and export a fresh token.

Once authentication succeeds, `Pipeline service access is required` means the sender lacks an active registration in dev's `servicePrincipals` table. A production database restore brings production registrations, not registrations for newly created dev senders. Register the approved dev sender with only `pipeline:publish` through the authorized operator workflow. Keep production and the existing write/target checks unchanged.

Set `BBPC_EXPECTED_CONVEX_URL` to the exact intended origin. For a remote deployment also set `BBPC_EXPECTED_CONVEX_DEPLOYMENT` to its deployment name. Preserve `BBPC_FORBIDDEN_CONVEX_DEPLOYMENT` from the existing rollout configuration. Local testing supports explicit localhost origins.

```sh
# Set the environment through your normal secret/configuration workflow first.
pnpm --filter @tonyisup/bbpc-convex-api transcripts:import \
  --source /absolute/path/to/transcripts \
  --mapping /absolute/path/to/mapping.json \
  --url "$BBPC_EXPECTED_CONVEX_URL"

# After reviewing that dry-run manifest:
pnpm --filter @tonyisup/bbpc-convex-api transcripts:import \
  --source /absolute/path/to/transcripts \
  --mapping /absolute/path/to/mapping.json \
  --url "$BBPC_EXPECTED_CONVEX_URL" --apply
```

Each completed episode is one atomic import batch: at most **400 passages**, **2,000 UTF-8 bytes per passage**, and **512 KiB of passage text including overlap**. Long files fail explicitly; they are never silently truncated. At most 400 old rows are deleted and 400 new rows inserted, plus metadata/audit writes. This was verified against a real isolated local Convex backend at the enforced maximum. Limits leave substantial headroom below [Convex transaction limits](https://docs.convex.dev/production/state/limits).

The 512 KiB source limit is an upper ceiling, not a guarantee that a transcript fits: 800-byte grouping and overlap can reach 400 passages sooner. The builder rejects that capacity overflow before creating a 401st passage, with an explicit size error before any backend requests.

The importer validates all source files and inspects all episode IDs before applying. Episodes are committed individually, so an interrupted multi-episode import may have completed earlier episodes. Rerunning is safe: identical content/version is a no-op. Transport retries reuse the same expected hash. Concurrent changes fail with a conflict and leave the newer transcript intact. Run another dry-run to deliberately accept the current baseline before replacing it.

Search rows contain only the current generation. Episode publication changes update indexed eligibility atomically, and public queries recheck canonical visibility. Deleting an episode through application mutations also removes its transcript. To explicitly remove a transcript or clean an orphan created outside application mutations, use the authenticated `episodes.transcripts.remove` mutation with `clientApiVersion`, `episodeId`, and the current `expectedHash` from `inspect` (or the prior import response if the episode no longer exists). Repeating removal is safe.

## Verify rollout

Search for three phrases from completed transcripts and confirm their episode and displayed timestamps. Existing title/movie results should remain visible. Transcript results show generated text and timestamps; timestamps do not seek playback. The first version returns up to 100 ranked passage hits, 20 episodes, and three nonoverlapping passages per episode, with a notice when the search is capped. It uses word/prefix matching rather than typo or semantic matching.

Automated checks:

```sh
pnpm --filter @tonyisup/bbpc-convex-api transcripts:test
pnpm --filter @tonyisup/bbpc-convex-api exec vitest run convex/transcripts.test.ts
pnpm --filter bbpc exec vitest run --config vitest.config.ts tests/TranscriptSearch.behavior.test.tsx tests/TranscriptRoute.behavior.test.tsx
```

All test transcripts are synthetic. Do not commit real transcript files, import manifests, tokens, or session data.
