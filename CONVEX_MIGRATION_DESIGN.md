## Problem Statement

BBPC has one product domain implemented as several partially divergent database contracts:

- `bbpc` and `bbpc-admin` each carry a 33-model Prisma schema backed by SQL Server.
- `bbpc-db` contains 33 table definitions, five views, and two stored procedures, but it is not fully aligned with either Prisma schema.
- `bbpc-pipeline` has nine Python files that use `pyodbc` directly.
- `bbpc-recording` already has an independent 11-table Convex backend with a custom participant-token authorization model.

The desired outcome is not merely to retire SQL Server. It is to establish one coherent backend that owns the schema, business rules, authorization boundaries, migrations, and API contracts for every BBPC application.

The prior assessment recommended a bounded hybrid Convex read model. That recommendation assumed a live, risk-minimizing migration. The chosen workflow is different: clone the production SQL Server database, work offline without time pressure, build full behavioral parity, and cut consumers over only after the Convex backend is proven.

## What Makes This Cool

The finished system has one place to understand and change BBPC:

```text
                              ┌─────────────────────────────┐
bbpc web ────────────────────▶│                             │
bbpc-admin ──────────────────▶│  bbpc-convex                │
bbpc-pipeline (Python) ──────▶│                             │
bbpc-recording ──────────────▶│  schema + functions + auth │
                              │  migrations + tests         │
                              └──────────────┬──────────────┘
                                             │
                                             ▼
                                   one Convex deployment
```

Application code stops owning persistence semantics. A scoring rule, role check, episode relationship, or ordered-list invariant is implemented once and consumed everywhere. A later monorepo consolidation can move the backend package without redesigning it.

## Constraints

1. **Production is authoritative.** The checked-in SQL project and Prisma schemas already disagree. The migration begins by introspecting the cloned production database, including tables, columns, defaults, checks, indexes, unique constraints, relationships, row counts, and orphaned data.
2. **No live dual-write layer.** The Convex backend is built in parallel from snapshots. The final production migration uses a planned read-only window and a fresh export.
3. **SQL identifiers cannot become Convex document IDs.** Every migrated record keeps an indexed `legacyId`; runtime relationships use Convex `Id<...>` values.
4. **Business semantics matter more than table similarity.** SQL views, stored procedures, Prisma transactions, raw queries, grouping, cascading behavior, and ordered updates must become tested Convex functions or maintained derived data.
5. **Convex transaction limits shape implementation.** Large imports, deletes, and recalculations must be bounded, resumable, and split into deterministic batches.
6. **The identity model is decided before the final data schema.** Provider selection may remain open briefly, but canonical users, provider identities, roles, impersonation audits, service principals, and the retirement of old sessions/tokens must be defined before domain records are transformed.
7. **Existing media storage remains separate by default.** Azure Blob objects and upload workflows are not moved merely because database metadata moves. This can be reconsidered as a separate project.
8. **The current applications are separate repositories and framework generations.** The shared backend cannot depend on frontend source paths, framework internals, or a single application deployment.
9. **Tests are currently uneven.** `bbpc` has one contract test, `bbpc-admin` has verification scripts but no configured unit-test command, and `bbpc-recording` has the strongest automated Convex coverage. Backend parity tests are part of the migration, not follow-up work.

## Premises

1. One standalone Convex project becomes the sole system of record for BBPC.
2. All consumers call backend functions; they do not receive direct table-level access.
3. The production SQL clone is the canonical input for discovery and rehearsal.
4. Offline parallel construction is safer here than a temporary SQL/Convex synchronization system.
5. Migration correctness requires both structural reconciliation and differential behavior tests against the SQL implementation.
6. `bbpc-recording` will join the shared deployment after the core identity and episode contracts exist; its session capability remains a separate domain module.
7. Repository consolidation is desirable later but does not need to block the database migration.
8. All SQL-backed production consumers switch together while writes are frozen. Consumer-by-consumer work happens only in local and staging environments.
9. Production rollback is available until the first post-S3 application/domain write.
   S1/S2 may perform only audited reversible restore, migration, reconciliation,
   smoke-identity, and control-state writes derived from frozen SQL. The first accepted
   application/domain write is the explicit point of no return; recovery after that point
   is forward-fix or Convex backup restore, not reopening a stale SQL snapshot.

## Conventional Wisdom and the BBPC Exception

**Layer 1:** Use a gradual cutover, index every bounded access path, put multi-record rules inside transactions, and keep external side effects outside transactional mutations.

**Layer 2:** Current Convex supports local deployments, JSONL imports, backup/restore, TypeScript and Python clients, transactional mutations, paginated reactive queries, and staged indexes. Local deployments and data import are still beta. Convex Auth and some Next.js authentication support are also beta or experimental.

**Layer 3:** A live strangler migration normally lowers risk. For BBPC, the user has chosen an offline, no-rush rebuild from a production clone. Adding dual writes would create conflict handling, replay, monitoring, and cleanup work that delivers no lasting value. The safer path is a deterministic snapshot-to-Convex pipeline, local and staging integration by consumer, then one coordinated production switch for every SQL writer.

## Approaches Considered

### Approach A: Expand `bbpc-recording`

Add the legacy BBPC domains to the working Convex backend in `bbpc-recording` and point the other projects at its deployment.

**Pros**

- Reuses a configured Convex project, generated API, tests, and deployment.
- Produces the first shared connection with the least repository setup.

**Cons**

- Makes a work-in-progress frontend repository the owner of every application's backend.
- Couples recording releases and experiments to core content, auth, and scoring changes.
- Makes a later monorepo move harder because the backend must first be extracted from an app.

### Approach B: Dedicated `bbpc-convex` Backend

Create a standalone TypeScript Convex project that replaces the ownership role of `bbpc-db`. It contains the schema, domain functions, migration tooling, reconciliation reports, automated tests, and a versioned client contract.

**Pros**

- Establishes one explicit source of truth independent of every UI.
- Gives Convex deployment and schema changes their own CI and release history.
- Can later move into `packages/convex-backend` in a monorepo with minimal structural change.
- Lets the two Next.js apps share typed function references while Python uses the same public API through the official client.

**Cons**

- Requires package/version plumbing before frontend work starts.
- Cross-repository changes need contract-version coordination until a monorepo exists.

### Approach C: Consolidate into a Monorepo Now

Move every project into one workspace and add the shared Convex package as part of the same change.

**Pros**

- Simplifies local linking, coordinated changes, and shared CI.
- Removes temporary cross-repository package publishing.

**Cons**

- Combines database semantics, repository history, dependency management, Python tooling, and all deployment pipelines in one migration.
- Makes failures and regressions harder to attribute.
- Expands scope without improving the correctness of the initial data conversion.

## Recommended Approach

Choose **Approach B now**, with explicit portability for **Approach C later**.

The standalone backend should expose two layers:

```text
Consumers
   │
   ├── TypeScript: @bbpc/convex client contract
   └── Python: small typed wrapper around ConvexClient
   │
   ▼
Public application functions
   │  validate arguments, authenticate, authorize, return stable DTOs
   ▼
Internal domain functions
   │  content, identity, reviews, games, rankings, syllabus, recording
   ▼
Convex tables, indexes, derived summaries, scheduled maintenance
```

Public queries, mutations, and actions are constructed through typed boundary builders,
not directly from Convex's raw public constructors. Builders require an explicit access
class, resolve the canonical identity, authorize the operation, inject audited actor
context, and enforce the global application write gate for every mutation. Internal,
migration-only, service, and recording-capability boundaries use separate builders with
their own required context. Lint/import rules prohibit raw public function constructors
outside the small set of approved boundary-definition modules, and tests prove each
builder's allow/deny behavior.

All public functions also use a shared structured domain-error contract. Each expected
failure has a stable code, a user-safe message, retryability metadata, and optional
validated safe details. Internal exception text, stack traces, credentials, and sensitive
record contents never cross the public boundary; logs use a separate incident ID. tRPC
compatibility adapters map domain codes to the corresponding `TRPCError`, and the Python
client maps them to typed exceptions. Contract tests cover every documented error code
and reject undeclared public error shapes.

Recommended backend modules:

- `identity`: users, roles, role assignments, impersonation policy
- `catalog`: movies, shows, ratings, tags
- `episodes`: episodes, links, bangers, audio-message metadata
- `reviews`: reviews, assignment reviews, extra reviews
- `assignments`: assignments and syllabus workflow
- `games`: seasons, game types, point types, points, guesses, gambling, quote submissions
- `rankings`: ranked-list types, lists, items, ordering
- `recording`: current recording sessions, participants, RTC state, manifests, favorites, uploads
- `migration`: staging schema, transformations, checkpoints, reconciliation, cleanup

Each public query contract includes the exact index/range it uses, its expected maximum
cardinality, pagination or bounded `take` behavior, and response-size budget. CI lint
rejects database `.filter()` and unapproved unbounded `.collect()` calls. Production-scale
tests assert document/byte/time budgets. Expensive stable aggregates such as point totals,
leaderboards, and dashboard summaries use narrowly scoped incrementally maintained
derived records when measured query plans cannot stay within those budgets; derived state
always has a deterministic rebuild and reconciliation check.

The public API is organized by capability, not by consuming application. During the
migration, `bbpc` and `bbpc-admin` keep tRPC as a temporary compatibility layer.
Existing handlers become thin adapters that call Convex and preserve every inventoried
observable response, error, authorization, and side-effect contract. After the shared
backend has stabilized in production, screens move to direct Convex queries and
mutations domain by domain. New UI work may use Convex directly where reactivity is
valuable. tRPC is removed after usage telemetry and contract tests show no remaining
callers; it is not part of the permanent architecture.

## Data Migration Design

The migration is a reproducible build pipeline:

```text
fresh production clone
        │
        ▼
SQL catalog + data extraction
        │
        ├── schema inventory
        ├── constraint inventory
        ├── row counts/checksums
        └── per-table JSONL
        │
        ▼
raw legacy staging tables in local Convex
        │
        ▼
dependency-ordered transformation
        │
        ├── insert root entities with legacyId
        ├── resolve legacy foreign keys to Convex IDs
        ├── insert child and join entities
        ├── build derived summaries
        └── record resumable checkpoints
        │
        ▼
structural + behavioral reconciliation
        │
        ▼
portable-snapshot scrub
        │
        ├── delete raw staging/checkpoints
        ├── require zero pending effects/jobs
        └── exclude deployment-local system/control state
        │
        ▼
canonical-only Convex backup preserving final IDs
```

The process must be repeatable against a fresh clone. A migration run records:

- source database fingerprint and extraction timestamp
- per-table row count and checksum
- transformer version
- batch checkpoints
- inserted, skipped, repaired, and rejected records
- every unresolved orphan or constraint violation
- reconciliation results

Import and transformation functions must be safe to resume. A repeated batch either produces the same result or detects that it was already applied.

The promotion backup contains canonical application data and explicitly approved S2
smoke identities only. Before it is created, raw staging and migration checkpoints are
deleted, pending side-effect intents and scheduled migration work must be zero, and
deployment-local system/control state is removed. Function builders deny writes when
`systemState` is absent. After restoring exact code/schema/configuration and the backup
to production, a protected initializer creates a fresh disabled `systemState` for the
new cutover run, then production reconciliation runs before S2. Cloud staging uses
synthetic data only.

Batch configuration is measured rather than global. The database census estimates row
width and relationship fan-out for each transformer; production-scale rehearsals select
and record per-table row/document/byte budgets with safety headroom below Convex limits.
Only dependency-independent tables or partitions run concurrently, under a recorded
global cap. A batch that approaches a limit can be reduced and retried from its prior
checkpoint without duplicating documents or effects. The source fingerprint,
transformer version, batch budgets, concurrency cap, and checkpoint sequence are all part
of the immutable migration-run manifest.

### Type, Null, Time, and Collation Rules

Before a transformer is written, the census produces an approved mapping matrix:

| SQL shape | Convex target | Required rule |
|---|---|---|
| `uniqueidentifier` primary key | `legacyId: string` plus Convex `_id` | Normalize UUID text to lowercase; all runtime references use `_id` |
| `date` | `YYYY-MM-DD` string | Preserve calendar date without timezone conversion |
| `datetime` / `datetime2` | UTC epoch milliseconds | Document the SQL source timezone and reject ambiguous conversions |
| `tinyint` / `smallint` / `int` | `number` | Validate original SQL range and domain-specific bounds |
| nullable scalar | optional or explicit union with `null` | Decide per field; never silently interchange absent and `null` |
| case-insensitive unique text | display value plus normalized key | Normalize trim, Unicode form, and case according to the production collation |
| filtered unique index | indexed lookup plus mutation check | Enforce uniqueness transactionally in every write function |

Round-trip fixtures cover every SQL type and every normalization rule. The migration fails on a value that cannot be represented without a recorded repair decision.

### Production-Data Handling

The clone and all extraction artifacts are sensitive production data:

- Keep the SQL clone and raw JSONL only on an approved, encrypted development machine.
- Exclude the clone, staging exports, backups, and reports containing personal data from Git and cloud sync.
- Never export Auth.js `refresh_token`, `access_token`, `id_token`, session tokens, or verification-token secrets.
- Do not migrate live recording invite tokens, participant access tokens, or admin secrets. Regenerate or invalidate them during the recording move.
- Migrate user profiles, verified identity links, and role assignments, but require every person to sign in again after cutover.
- Redact emails, tokens, URLs with credentials, and free-form personal content from logs.
- Restrict migration credentials to local/dev deployments until the final controlled production run.
- Delete raw extracts and temporary staging tables after the retention period recorded in the go/no-go report.
- Record who ran each production extraction, transformation, restore, and deletion without recording secret values.

### Behavior Census and Differential Parity

Database parity is insufficient because business behavior currently lives in routers, helpers, SQL, upload handlers, and scripts. Before Convex domain functions are implemented, generate a machine-readable operation census for:

- all public and protected procedures in the 16 `bbpc` routers
- all procedures in the 23 `bbpc-admin` routers
- direct database reads in pages, server rendering, authentication callbacks, and upload handlers
- all nine `bbpc-pipeline` files that use `pyodbc`
- all production views, stored procedures, raw SQL calls, and background scripts
- the existing `bbpc-recording` Convex API

Each operation records:

- caller and user-visible workflow
- input validator and representative fixtures
- intended authentication and authorization rules
- tables, indexes, and derived data read
- writes, uniqueness rules, cascades, and ordering rules
- response DTO and error outcomes
- external effects such as Azure Blob, UploadThing, email, Pusher, or webhooks
- expected behavior for missing, duplicate, stale, unauthorized, and concurrent inputs

Critical writes, auth decisions, leaderboards, points, guesses, gambling, assignments, ranked-list ordering, syllabus ordering, quote submissions, and destructive admin operations require differential tests. The same fixture is run against the SQL implementation and Convex, then normalized results, persisted state, errors, and emitted side-effect intents are compared.

When the two applications, SQL artifacts, or helpers disagree, the migration does not
silently choose one implementation or preserve unnamed variants. The parity report
records the conflicting outputs, representative production impact, and an explicit
disposition for the canonical rule. Both consumers then call the same Convex domain
operation. A legitimate contextual difference must be represented as a named parameter
or separately named use case with its own contract and tests.

Acceptance is:

- 100% of inventoried operations have a migrate, adapt, or retire disposition
- 100% of callable operations are explicitly classified as anonymous,
  authenticated-owner, admin, pipeline-service, recording-capability, or internal;
  unclassified operations fail CI and are not exported
- zero unexplained row-count or relationship mismatches
- zero unreviewed rejected records
- zero migrated credential or session secrets
- exact agreement on integer/scoring results and authorization decisions
- DTO agreement except for approved, documented differences
- no user-facing p95 latency regression greater than 20% on production-scale fixtures, and every Convex function stays below platform transaction and execution limits

The verification stack is layered by runtime:

- `bbpc-convex` uses Vitest and `convex-test` for domain, validator, index,
  authorization-builder, mutation, query, scheduler, and failure-path coverage.
- `bbpc` and `bbpc-admin` use Vitest for compatibility adapters and Playwright for
  cross-component critical user and administrator flows.
- `bbpc-pipeline` retains pytest and adds contract tests for the typed Convex wrapper,
  Clerk M2M authentication, retries, error mapping, and idempotency.
- `bbpc-recording` retains its existing Vitest and `convex-test` foundation when it
  moves later.
- New migration/backend code and every changed compatibility adapter require 100%
  branch coverage; critical auth, destructive, data-migration, and cutover flows also
  require integration or end-to-end coverage where mocks would hide failures.

Fixtures have two trust tiers. Source-controlled synthetic fixtures are deterministic,
contain no production-derived values, and exercise every mapping, branch, boundary, and
error in CI. Separately, differential tests and full-scale rehearsals run only on the
approved encrypted machine against the isolated production clone. Those runs emit
redacted counts, checksums, timings, and disposition identifiers—never raw rows,
emails, tokens, URLs with credentials, or free-form production content.

Every application route receives an authenticated or anonymous smoke test as applicable.
End-to-end coverage is concentrated where mocks could hide integration failures:
Clerk sign-in and verified legacy-user linking; core user writes; administrator, role,
ordering, and destructive workflows; stale and concurrent submissions; pipeline M2M
authentication and retries; side-effect success, retry, terminal failure, and recovery;
and cutover write-gate transitions including stale clients and direct HTTP callers.
All remaining branches are covered by faster unit, function, adapter, and contract tests.

Recovery tests use deterministic failpoints rather than happy-path assertions alone.
They interrupt extraction and transformation before and after checkpoints; redeliver
imports and side-effect intents; expire or revoke user and machine tokens; fail adapters,
remote storage, package publication, and deployment steps; and exercise every S1–S3
cutover transition with stale clients. Each case asserts safe retry, exact reconciliation,
correct terminal status, no duplicate effect, and an actionable audit trail. Rehearsals
also restore an actual Convex backup into a disposable deployment and rerun acceptance
checks against the restored state.

Authorization parity means parity with the approved intended policy, not with accidental
legacy exposure. The operation census must flag any mutation implemented as an
unprotected tRPC procedure, any read that may expose personal or administrative data,
and any operation whose ownership rule is implicit. Those cases require an explicit
policy disposition before their Convex replacement is implemented. Known legacy
unauthenticated writes are security defects and are never reproduced as public Convex
functions.

### External Side Effects

Convex mutations cannot safely perform network side effects inside their transaction. Any workflow combining a database write with Azure Blob, UploadThing, email, Pusher, or a webhook uses a durable side-effect queue: the mutation records an intent and an idempotency key in the same transaction, then a scheduled action performs it after commit.

Each side effect defines:

- idempotency key and duplicate behavior
- retry policy and terminal failure state
- compensation or operator recovery action
- reconciliation job for remote state versus Convex state
- user-visible pending and failure states
- audit fields linking the intent to the initiating user or service

Pusher is retired where Convex subscriptions replace it. Azure Blob and UploadThing remain the media stores unless separately migrated.

## Backend Contract Distribution

Before a monorepo:

- `bbpc-convex` owns generated Convex function references and data-model types.
- Backend CI deploys backward-compatible functions to staging, then uses the official beta multi-repository flow (`npx convex-helpers ts-api-spec`) to generate a client-only API specification.
- CI publishes that specification and stable DTO helpers as `@tonyisup/bbpc-convex-api` through GitHub Packages.
- Convex and `convex-helpers` versions are pinned in the backend lockfile. Package
  publishing fails closed if generation, validation, or consumer contract checks fail.
  A tooling regression freezes dependency upgrades; it does not replace or remove the
  last published package or its compatible deployed backend.
- `bbpc` and `bbpc-admin` pin an explicit package version.
- `bbpc-pipeline` owns a small Python wrapper whose methods correspond to stable public backend functions.
- `bbpc-recording` consumes the same TypeScript contract after its functions move.
- Backend production deployment happens from `bbpc-convex` CI, not from a frontend build.

Contract policy:

- Every public function has argument and return validators.
- Additive functions and optional response fields are minor versions.
- Removed functions, renamed arguments, and incompatible response changes are major versions.
- Deployment order is backend-compatible code, generated API package, consumer upgrades, usage verification, then removal in a later major release.
- Old public functions remain available until every pinned consumer version has moved and contract telemetry/tests show no remaining callers.
- Each consumer runs contract compilation and representative calls against staging before merge.
- Package rollback means pinning the prior client version while the backward-compatible backend remains deployed.

After a monorepo:

- The backend moves to `packages/convex-backend`.
- The client package becomes a workspace dependency.
- Function names, DTOs, deployment ownership, and data do not change.

## Authentication Direction

The provider-neutral identity model is fixed before finalizing domain tables:

- `users` stores the canonical BBPC person and the SQL `legacyId`.
- `authIdentities` maps a unique `(issuer, subject)` identity to one user and records the verified email at link time.
- Account linking requires an authenticated existing identity or an explicit audited admin action; matching an unverified email is never sufficient.
- `roles` and `userRoles` remain explicit domain data enforced inside Convex functions.
- Current persistent `impersonatedUserId` state is replaced by expiring, audited impersonation sessions containing actor, target, reason, start, end, and revocation.
- Auth.js accounts may be used to establish verified provider links, but Auth.js sessions, verification tokens, OAuth access tokens, refresh tokens, and ID tokens are retired rather than copied.

The authentication provider is selected before transformation code for users is finalized. Provider selection follows the identity contract rather than changing it.

The target must support:

- Google sign-in and email sign-in or a deliberate replacement
- one stable external identity mapped to one Convex user
- server-rendered and client-side authenticated Convex calls
- shared sessions or equivalent identity across `bbpc` and `bbpc-admin`
- role checks enforced inside Convex functions
- safe admin impersonation with auditability and no privilege inheritance
- a dedicated `bbpc-pipeline` service identity
- recording invite/participant capabilities that cannot escalate into account privileges

Clerk is the selected identity provider. The migration will use the existing Clerk application
`app_2XzsQIxG2mvqYQ1ZNxqQMUsw89u`, with separate development and production
configuration and secrets. Clerk identity remains provider-facing; canonical users, roles,
impersonation policy, and authorization remain owned by Convex. At first post-cutover sign-in,
a verified Clerk identity is linked to the migrated BBPC user through the provider-neutral
identity contract above.

`bbpc-pipeline` authenticates with a short-lived Clerk machine-to-machine token.
A Convex HTTP action verifies the token and maps its machine subject to a
`servicePrincipals` record containing explicit permissions such as `catalog:read`,
`episodes:read`, and `episodes:metadata:write`. Only the HTTP boundary is public;
it invokes internal queries, mutations, and actions after identity, expiry, audience,
permission, write-gate, and replay-sensitive checks pass. Normal user tokens are
rejected for service-only operations, and pipeline tokens cannot call admin or unrelated
domain functions. Every service mutation is audited. Production code never receives a
Convex deployment admin key.

## Production Cutover and Point of No Return

Production does not switch one consumer at a time:

```text
S0  SQL writable, production apps use SQL
 │  Convex is local/staging only
 ▼
S1  Freeze every SQL writer; apps enter maintenance/read-only mode
 │  Fresh extract, transform, restore, indexes, reconciliation
 ▼
S2  All SQL-backed consumers point to Convex with writes still disabled
 │  Smoke tests; create, download, and verify an S2 production backup
 │  Restore that backup into a disposable deployment and record the result
 │  Signed go/no-go report names the backup, checksum, retention, and restore command
 ├── failure: point consumers back to frozen SQL, then unfreeze SQL
 ▼
S3  Enable Convex writes for all consumers
 │  FIRST APPLICATION/DOMAIN WRITE = POINT OF NO RETURN
 ▼
S4  Forward-fix or restore a Convex backup; SQL remains an archive
```

`bbpc-admin`, `bbpc`, and `bbpc-pipeline` must all be on compatible Convex builds before S1. `bbpc-recording` is a separate existing data domain and may move later, but it cannot write legacy SQL.

`bbpc-recording` will move after the SQL-backed production cutover as a separate
release. Until then its current Convex deployment remains isolated. After the shared
backend is stable, recording data and functions are transformed into the canonical
episode and identity model, its participant capabilities are regenerated, and the old
recording deployment is retired only after reconciliation and acceptance testing.

The write gate is enforced in the backend, not only in UI configuration. A singleton `systemState` document records `applicationWriteMode`, `cutoverRunId`, and audit fields. Every public user mutation, pipeline service mutation, scheduled job, and side-effect dispatcher calls a shared `requireApplicationWritesEnabled` guard. Only a separately protected internal cutover function can change the gate. Tests prove that browsers, service tokens, scheduled work, direct HTTP clients, and stale application builds cannot bypass disabled mode. Migration-only internal functions use a separate explicit confirmation and never become public API.

The SQL database is a rollback target through S2 because all permitted Convex writes in
S1/S2 are audited, reversible snapshot/control setup derived from frozen SQL; application
mutations, scheduled domain work, and external effects remain blocked. After the first
post-S3 application/domain write, reopening SQL would discard newer data and is
forbidden. Recovery then uses a known-good backend release, Convex backup restore,
targeted repair mutations, or a forward patch.

After the database census, set a cutover service-level objective covering maximum read-only duration and maximum time for each stage. Run two full production-scale rehearsals from fresh clones. Both must finish within the objective and produce identical acceptance results before S1 is scheduled.

Performance is a hard cutover gate. Before implementation changes behavior, capture
representative SQL p50/p95/p99 latency, payload size, and concurrency baselines. For each
Convex operation and full rehearsal, record latency, response bytes, documents and bytes
scanned, transaction conflicts/retries, side-effect queue age, batch throughput, and total
migration duration. Both production-scale rehearsals must remain within Convex budgets,
show no unexplained user-visible p95 regression greater than 20%, and meet the
read-only/cutover objective approved after measured rehearsal data exists. Functional
parity alone cannot waive these gates.

## Success Criteria

The migration is complete only when:

1. One Convex production deployment is the sole writable system of record for all four projects.
2. All 33 production tables and every production-only artifact have an explicit disposition: migrated, transformed, merged, or intentionally retired.
3. Every SQL view, stored procedure, raw SQL query, Prisma transaction, group, aggregate, cascade, uniqueness rule, and ordering workflow has a tested replacement or an explicit retirement decision.
4. Fresh-clone migration is repeatable and resumable with no unexplained row loss.
5. Reconciliation reports meet the explicit parity thresholds, and every inventoried operation has a tested replacement, compatibility adapter, or retirement decision.
6. `bbpc` and `bbpc-admin` no longer depend on Prisma, `@prisma/adapter-mssql`, `mssql`, or `DATABASE_URL`.
7. `bbpc-pipeline` no longer imports `pyodbc` for BBPC application data.
8. `bbpc-recording` uses the shared deployment and links sessions to canonical users/episodes where appropriate.
9. Authorization is enforced in Convex functions and covered by negative tests.
10. SQL rollback is rehearsed through cutover state S2, and the S3 point of no return is
    explicitly approved before Convex accepts an application/domain write.
11. Backend deployment, backup, environment configuration, and client-contract release procedures are documented and exercised.
12. A later monorepo consolidation requires no backend schema or API redesign.

## Distribution Plan

- Develop against a local Convex deployment committed only through source-controlled schema and functions; local state remains ignored.
- Maintain separate local/dev, staging, and production deployments.
- Run schema validation, TypeScript checks, Convex tests, migration fixture tests, and contract tests in `bbpc-convex` CI.
